# Paseo 병렬 팀 운영 (3계층)

> **시험 운영 전이다.** 이 스킬은 Orca 용으로 검증된 절차를 Paseo 의 명령으로 옮긴 것이고, 옮긴 뒤 한 번도 돌려 보지 않았다. Paseo 도움말·문서에서 직접 확인한 명령과 옵션만 단정해 적었고, 확인하지 못한 것은 「미측정」 으로 표시해 끝의 §7 에 모았다. **처음 쓰기 전에 읽기 전용 시험 1회**(워커 1명 ＋ 이름 있는 팀원 2명의 왕복 ＋ 창구와의 교신, §0 6번)를 돌려 §7 의 첫 항목들을 먼저 확인한다. 시험에서 확인된 것은 §7 에서 지우고 본문에 반영한다.

## 구조

| 층 | 누구 | 하는 일 | 하지 않는 일 |
| --- | --- | --- | --- |
| 창구 | 메인 세션(Paseo 안에서 연 Claude 에이전트 세션) | 트랙 설계 · 워커 기동 · 워커 보고 수령과 결재 · 공유 자원(풀스위트 · 포트 · 브라우저) 슬롯 배정 · 머지 · 결정 기록 · 전체 지휘 · 끝난 워커 종료 | 코드 직접 수정(결함은 좌표와 함께 담당 워커에게) · 맡길 수 있는 조사·검증·진단(「창구 컨텍스트 보호」) |
| 워커 | 트랙 작업 공간(git worktree)에 `paseo run` 으로 띄운 독립 Claude 세션 = 트랙 팀 리드 | 역할 팀원 spawn · 배정 · 순서 관리 · 도메인 탐색 · 최종 판정 · 창구 교신 | 역할 칸(분석 · 설계 · 검증 · 구현 · 리뷰)을 직접 채우기 |
| 팀원 | 워커가 `Agent` 도구에 `name` 을 주어 spawn 한 agent team 팀원 | 자기 역할 산출물을 파일로 쓰고 커밋 · 팀원끼리 이름으로 `SendMessage` | 다른 역할 겸직 |

- 왜 agent team 인가 — 팀원끼리 직접 주고받아(예: plan-architect ↔ plan reviewer 핑퐁) 워커와 창구가 중계하지 않는다. 워커는 결론만, 창구는 결론의 요약만 받아 컨텍스트가 보호되고, 검증이 설계·구현과 분리된다.
- 워커는 창구 팀의 팀원이 아니라 독립 세션이라 스스로 팀 리드다. 그래서 이름 있는 팀원을 만들 수 있다(tmux pane 기반 도구에서 워커가 팀원이면 「팀원은 팀원을 못 만든다」 제약에 걸린다). 이 조건이 Paseo 에서 성립하는지는 다음과 같다.
  - **문서로 확인함**: Paseo 가 띄운 에이전트(Paseo 서브에이전트)는 「대화할 수 있는 완전한 에이전트 세션」 이고, 공급자 안에서 만드는 네이티브 서브에이전트(읽기 전용 타임라인)와 따로 구분된다. Claude 공급자는 공식 `claude` CLI 와 Claude Agent SDK 로 실행되고 사용자의 구성 · 스킬 · MCP 서버가 그대로 유지된다고 적혀 있다. 즉 워커는 창구의 팀원이 아니라 별도 세션이다.
  - **미측정**: 그 세션 안에서 `Agent` 도구로 이름 있는 팀원을 만들고 `SendMessage` 가 동작하는지는 Paseo 문서에 없다. 시험 1회의 첫 확인 항목이다(§0 6번, §7).
- 용어 주의 — Paseo 문서의 「서브에이전트」 는 창구가 `paseo run` 으로 만든 **워커**(Paseo 가 부모-자식 관계를 추적하는 별도 세션)를 뜻한다. 이 스킬의 「팀원」 은 워커가 Claude Code 의 `Agent` 도구로 만드는 이름 있는 agent team 팀원이다. 둘을 섞어 쓰지 않는다.
- 전제 — 창구와 워커는 모두 Paseo 의 `claude` 공급자 세션이다(`Agent` 도구 · `SendMessage` 가 Claude Code 기능이므로). 다른 공급자(Codex 등)는 이 스킬 범위 밖이고 미측정이다.

## 창구 컨텍스트 보호 — 메인 세션이 꼭 할 일이 아니면 맡긴다

창구(메인 세션)는 사용자와 가장 오래 대화하는 세션이다. 창구가 직접 일하면 컨텍스트가 빨리 차서 요약되고, 요약될 때마다 앞선 결정과 세부가 깎인다. 그래서 창구가 꼭 해야 하는 일이 아니면 별도 에이전트(`Agent`, `model: sonnet`, fork 금지)를 띄워 맡기고 결론만 받는다.

| 구분 | 일 |
| --- | --- |
| 맡긴다 | 여러 파일을 읽어야 답이 나오는 조사 · 브라우저 테스트와 실제 요청 시험 · 빌드나 배포가 끝나기를 기다렸다 하는 검증 · 시행착오가 예상되는 진단 · 문서와 규칙 파일의 초안 · 긴 워커 보고의 요약(결정 항목과 막힌 점만) · 머지 직전 수치 재측정(「판정 술어」) |
| 창구가 한다 | 사용자와의 대화, 승인과 결정 중계 · 워커 기동과 지시, 공유 자원 슬롯 배정 · push · MR · 머지 · 배포(접근 권한이 창구에만 있고 되돌리기 어렵다) · 도구 호출 두세 번으로 끝나는 확인 |

- 맡긴 결과 중 **설계나 배포 판단이 기대는 사실**은 창구가 한 번 더 확인한다. 요약은 틀린 내용도 맞는 내용과 같은 말투로 돌아온다.
- 비밀값을 다루는 일은 지시문에 「값을 출력하지 않는다」 를 적어 맡기거나, 범위가 작으면 창구가 직접 한다.
- 지시문은 그것만 읽고 일할 수 있게 쓴다(목표 · 이미 확인한 것 · 볼 파일 · 하지 말 것 · 보고 형식). 지시문을 쓰는 비용이 직접 하는 비용보다 크면 직접 한다.
- 한꺼번에 많이 띄우지 않는다. 팀원과 에이전트는 같은 사용 한도를 나눠 쓴다.

## 사용자에게 묻는 기준 — 중간에 멈추는 횟수를 줄인다

질문 하나마다 작업이 멈춘다. 추천안이 분명한 기술적 선택까지 물으면 사용자는 추천안을 고르는 일만 반복하게 된다.

| 구분 | 내용 |
| --- | --- |
| 묻는다 | 되돌리기 어려운 일 · 범위나 일정이 달라지는 일 · 사용자가 화면에서 느끼는 동작이 바뀌는 일 · 비용, 외부 설정, 실데이터 쓰기가 필요한 일 |
| 묻지 않는다 | 그 밖의 기술적 선택. 추천안대로 진행하고 승인 요청 때 「이렇게 정했다」 목록으로 보고한다. 사용자는 이견이 있을 때만 말한다 |

- 프로젝트가 정한 승인 게이트(예: 요구사항 승인, plan 승인)는 이 기준과 무관하게 그대로 받는다.
- 워커 명세에도 같은 기준을 적는다. 워커가 창구로 올리는 질문이 줄어야 창구가 사용자에게 올리는 질문도 준다.
- 품질을 낮춰 속도를 얻는 변경(역할 합치기, 검수 순서 바꾸기, 단계 건너뛰기)은 창구나 워커가 스스로 정하지 않는다. 묻는 항목이다.
- 워커가 권한 요청(`paseo permit ls` 에 뜨는 것)에서 멈췄을 때 허용할지도 이 기준으로 판단한다. 되돌리기 어렵거나 외부에 영향을 주는 요청이면 사용자에게 묻는다.

## 모델

| 층 | 모델 | 지정 방법 |
| --- | --- | --- |
| 창구 · 워커 | 사용자가 설정한 모델 그대로 | 창구가 모델을 새로 고르거나 바꾸지 않는다. Paseo 는 에이전트를 만들 때 공급자를 정해야 하므로 워커의 공급자만 `claude` 로 하고, 모델 · 모드 · 사고 수준은 사용자가 정한 값(사용자가 지명한 에이전트 프로필의 launch 설정)을 그대로 쓴다. 모델 칸이 비어 있으면 임의로 정하지 않고 사용자에게 묻는다 |
| 팀원 | **항상 최신 Sonnet** | spawn 할 때마다 `Agent` 도구의 `model` 에 `sonnet` 별칭을 준다 |
| 이름 없는 서브에이전트 | **항상 최신 Sonnet** | 창구 · 워커 · 팀원 누가 띄우든 `Agent` 도구의 `model` 에 `sonnet` 을 준다(짧은 조회 · 탐색 · 검증 대행 모두) |

- 버전 ID 를 고정해 적지 않는다. 별칭이 최신 Sonnet 으로 풀리므로 새 Sonnet 이 나와도 고칠 곳이 없다.
- `model` 을 빠뜨리면 팀원 · 서브에이전트는 띄운 쪽 모델을 물려받는다(서브에이전트 기본 모델을 따로 설정하지 않은 환경 기준) ⇒ 생략은 곧 위반이다.
- 팀원 · 서브에이전트를 `fork` 로 만들지 않는다. fork 는 `model` 을 무시하고 띄운 쪽 모델로 돈다.
- 에이전트 정의 파일(`.claude/agents/*.md`)의 `model` 보다 `Agent` 도구의 `model` 이 우선한다. 정의 파일이 다른 모델이어도 spawn 때 `sonnet` 을 주면 Sonnet 으로 돈다.
- Paseo 가 띄운 Claude 세션에서도 위 별칭이 같게 풀리는지는 미측정이다. §3 3번(고유 토큰 왕복에서 자기 모델명을 답하게 하기)이 그 확인을 겸한다.

## 역할 (프로젝트에 맞게 고른다)

- 겸직 금지 필수 5 = `plan-architect`(설계) · `plan reviewer`(설계 독립 검증) · `analyzer`(현행 코드·요구 분석) · `reviewer`(코드 리뷰) · `security`(보안 검수, 아래 「보안 검수」 절). 설계자와 구현자가 같으면 자기 설계를 검증하지 못하고, 게이트가 무엇을 못 보는지는 만든 사람이 제일 못 본다.
- 축별 dev(FE · BE · 도메인). `tester` 는 **화면이 있는 트랙에만** 둔다 — 하는 일은 실제 화면 관측(로컬 브라우저 테스트)과 계약 대조다. 화면이 없는 트랙(API · 워커 · 배치)에는 두지 않는다. 수치(타입체크 · 빌드 · 단위 시험)의 독립 재측정은 tester 가 아니라 창구가 머지 직전에 한다(「판정 술어」).
- 착수 때 전원 spawn 한다. 「필요해지면 그때」는 나중 역할(tester · reviewer · security)이 빠진다.
- `plan reviewer` 는 원천(코드·요구)을 직접 읽고 자기 예상을 먼저 적은 뒤 plan 과 대조한다(plan 이 답을 미리 주지 못하게).
- `reviewer` 프롬프트에 이 문장을 원문 그대로 넣는다: "Try to construct a code change that is WRONG but keeps the new tests green — if you find one, that is the most valuable thing you can report." 리뷰어도 틀리므로 결론은 반증 확인한다.
- 「틀린 구현 만들어 보기」 는 **reviewer 만, 리뷰 단계에서 한 번** 한다. dev 가 커밋마다 하거나 tester 가 따로 반복하지 않는다(같은 점검을 여러 역할이 반복하면 시간만 늘고 새 발견이 없다).

## 보안 검수 (security)

역할 · 단계 · 판정 · 지적 처리의 정본은 이 절이다. 점검 항목은 이 절에 적지 않고 두 층의 체크리스트를 참조한다 — 공통 = **스킬 체크리스트**, 프로젝트마다 다른 것(스택별 항목 · 등급 보정 · 보고서 경로 · 금지 동작) = **프로젝트 체크리스트**.

| 항목 | 규칙 |
| --- | --- |
| 스킬 체크리스트 | 이 스킬 폴더의 `security-checklist.md` — 등급 기준 · 공통 점검 항목. 먼저 읽는다. 창구가 설치된 위치의 절대경로를 워커 명세에 적는다 |
| 프로젝트 체크리스트 | `{프로젝트 루트}/docs/security-review/checklist.md` — 프로젝트 루트 = 그 프로젝트의 최상위 `CLAUDE.md` 가 있는 디렉터리(여러 저장소를 모은 워크스페이스면 그 루트). 창구가 워커 명세 「먼저 읽을 문서」 에 절대경로로 적는다(트랙 worktree 는 프로젝트 루트 밖에 있다). 스킬 체크리스트 다음에 읽고, 겹치거나 다르면 프로젝트 쪽이 우선한다 |
| 위치 | 코드를 바꾸는 트랙이면 항상. `reviewer` 통과 직후 → 워커 최종 판정 앞 |
| 범위 | 기준 브랜치 대비 diff ＋ 그 diff 로 **새로 열리거나 동작이 바뀐 경로 전체**(진입점 → 서비스 → 쿼리 · 큐 · 외부 호출). diff 줄만 보면 인증 누락 · IDOR 을 놓친다. 지적마다 「이번 diff」 와 「기존 코드」 를 구분한다 |
| 판정 | PASS = 긴급 · 높음 0건 / REQUEST CHANGES / ESCALATE |
| 재검수 | dev 가 고치면 reviewer → security 를 둘 다 다시 돈다. 테스트 범위가 바뀌면 tester 부터 |

**지적 처리** — 기본은 팀원끼리, 판단이 필요한 것만 워커에게.

- dev 에게 바로(워커는 참조): 이번 diff 에서 생긴 긴급 · 높음이고 plan 범위 안에서 고칠 수 있는 것.
- 워커 판단(dev 에게 직접 보내지 않는다): 기존 코드에 있던 취약점(창구 → 사용자, 별도 트랙) · plan 이나 요구가 바뀌는 수정(설계 게이트로 되돌림) · 결제 · 재화 · 인증 영역(워커가 직접 교차 검증) · dev 이견이나 같은 지적 핑퐁 2회 초과 · 중간 · 낮음 등급(이번에 고칠지 후속으로 넘길지).

**프롬프트에 넣을 것**

- 시작할 때 매번 스킬 체크리스트 → 프로젝트 체크리스트 순서로 절대경로를 읽는다(프롬프트에 항목을 복사하지 않는다 — 체크리스트를 고치면 바로 반영되게). 프로젝트 체크리스트가 없거나 항목이 비어 있으면 「프로젝트 항목 없음 · 전역 기준으로 검수」 를 판정문에 적는다.
- 코드 수정 · 커밋 금지(검수 전용). 운영 · 공유 환경 호출, 실데이터 쓰기, 실제 문자 · 메일 발송 금지 — 재현은 로컬 스텁으로만.
- 비밀값을 보고서 · 메시지에 옮기지 않는다. 취약점 상세(위치 · 재현)는 **저장소 밖** 보고서 파일에만 쓴다(「결론의 정본은 커밋된 파일」 규칙의 예외 — 저장소 · 커밋 메시지에 남기지 않는다). 경로는 프로젝트 체크리스트가 정하고, 없으면 워커가 저장소 밖 경로를 정해 준다.
- **검수 요약**(상세 없이 판정 · 정책별 결과 · 조치 커밋 · 넘긴 건)은 보고서 끝에 따로 적는다. 감사 증적(예: ISMS)이 필요한 프로젝트는 체크리스트가 정한 곳(예: 이슈 트래커 댓글)에 이 요약을 남긴다 — 남기는 사람과 시점도 체크리스트를 따른다. 정한 곳이 없으면 워커가 창구에 묻는다.
- 기존 코드에서 찾은 취약점(ESCALATE)은 사용자 승인을 받아 별도 이슈로 등록해 개선 이행을 추적한다. 이슈 본문에는 대상 기능 · 유형 · 등급까지만 적고 재현 절차는 적지 않는다.
- 체크리스트 정책마다 「해당 없음 / PASS / FAIL」 을 근거(파일:라인 또는 해당 없는 이유 한 줄)와 함께 적는다 — 건너뛴 정책이 남지 않게. 정책에 없는 취약점을 찾아도 보고한다.
- 지적마다: 등급 · 정책 ID(목록 밖이면 「목록 외」) · 파일:라인 · 공격 시나리오 한 줄 · 수정 방향 · 이번 diff / 기존 코드. 코드 붙여넣기 금지.
- 워커에게 결론 1통(판정 ＋ 건수 ＋ 보고서 경로).

## Paseo 수단 대응표 (기존 Orca 명령 → Paseo)

기존 절차가 도구에 바라는 일은 여섯 가지다. 아래 표는 그것을 Paseo 의 CLI(셸이 있으면 항상 쓸 수 있다)와 MCP 도구(Settings → Host → Tools & prompts 에서 「Enable Paseo tools」 를 켠 경우)로 옮긴 것이다. 「확인」 열은 `paseo --help` 와 하위 명령 도움말, Paseo 공개 문서에서 직접 읽었는지를 뜻한다. 읽었다고 해서 실제로 돌려 본 것은 아니다.

| 기능 | CLI | MCP 도구 | 확인 |
| --- | --- | --- | --- |
| 워커 띄우기 | 먼저 `paseo workspace create --isolation worktree --path <저장소> --mode branch-off --new-branch <브랜치> --base <기준 ref>` 로 트랙 작업 공간을 만든 뒤 `paseo run --workspace <workspace-id> --provider claude --title <라벨> --label <키=값> --env <키=값> --no-wait --quiet "<첫 지시>"` (ID 가 출력된다) | `create_workspace` → `create_agent`(`title` · `provider` · `initialPrompt` · `workspaceId` · `labels` · `settings`) | 도움말·문서에서 확인함 |
| 창구 → 워커 | `paseo send <워커 id> --no-wait "<본문>"` 또는 `--prompt-file <경로>`. 급할 때만 `--behavior steer` · `interrupt` | `send_agent_prompt`(`agentId` · `prompt` · `activeTurnBehavior`) | 확인함 |
| 워커 → 창구 | 같은 `paseo send <창구 id> --no-wait ...`. 에이전트는 ID 로 다른 에이전트에게 프롬프트를 보낼 수 있다(자기가 만들지 않은 에이전트에게도). 종류 구분은 없다(아래 둘째 표) | 같음. 워커 완료 · 오류 · 권한 요청은 `notifyOnFinish`(기본 true)로 부모에게 알림 | 전달 수단 확인함 · CLI 경로 알림은 미측정 |
| 받은 것 기다리기 | 창구가 턴을 끝내고 알림·메시지를 기다린다(문서 권장 — 폴링하지 않는다). 한 워커의 턴 종료만 `paseo wait <id> --timeout <초>` 로 백그라운드에서 기다릴 수 있다 | (알림) | 확인함. 종류별 필터는 없다 |
| 워커 상태 보기 | `paseo ls`(`--label` · `-a` · `-g`) · `paseo inspect <id>` · `paseo logs <id> --tail <n>`(`--filter tools/text/errors/permissions`) · `paseo attach <id>` | `list_agents` · `get_agent_status` · `get_agent_activity` | 확인함 |
| 워커 끝내기 | `paseo archive <id>`(실행 중이면 `--force`) · `paseo workspace archive <workspace-id>`. 턴만 끊기 = `paseo stop <id>`, 영구 삭제 = `paseo delete <id>` | `archive_agent` · `archive_workspace` · `cancel_agent` · `kill_agent` | 확인함 |
| 사용 한도 | `paseo usage`(= `usage ls`, `--refresh` · `--json` · `--agent <id>`) | — | 명령 확인함 · Claude 5시간·주간 창이 나오는지는 미측정 |
| 권한 요청 | `paseo permit ls` · `permit allow <agent> [req_id]` · `permit deny` | `list_pending_permissions` · `respond_to_permission` | 확인함 |
| 정기 점검 | `paseo heartbeat create --cron "<5필드>" --max-runs <n> --expires-in <기간> "<프롬프트>"` · `heartbeat delete <id>` | `create_heartbeat` · `delete_heartbeat` | 확인함 |

**Paseo 에 대응 수단이 없어 규칙으로 메우는 것** — 「대응 수단 없음 — 이렇게 메운다」.

| 기존 절차가 쓰던 것 | Paseo | 메우는 방법 |
| --- | --- | --- |
| 메시지 종류(ask · status · merge_ready · escalation · worker_done) 구분과 종류별 수령 | 대응 수단 없음 — 모든 메시지가 같은 프롬프트다 | 모든 메시지 첫 줄에 종류 헤더를 붙이고 창구가 헤더로 거른다(§4) |
| 질문에 답이 왔는지 추적 | 대응 수단 없음 | 질문 번호 ＋ 창구의 대기 질문 파일 ＋ 답이 없으면 같은 번호로 재전송(§4) |
| 수신 확인과 같은 배치 재전송 방지 | 대응 수단 없음 | 메시지 번호로 중복을 거르고, 처리한 번호를 라운드 기록 파일에 적는다 |
| 라운드(Run) 단위 묶음 | 대응 수단 없음(에이전트에 붙이는 라벨은 있다) | 모든 워커에 `--label round=<이름>` 을 붙이고 `paseo ls --label round=<이름>` 으로 묶어 본다 |
| 워커가 보고 없이 멈춘 것 감지 | 턴 종료 · 오류 · 권한 요청 알림은 문서에 있다. 턴이 길게 이어지는 무보고 상태는 알림이 없다 | 창구 하트비트로 정기 점검(§1 5번) |
| 권한 확인 화면에 걸린 것 알림 | 권한 요청 알림 ＋ `paseo permit ls` | 알림 모양은 미측정. 걸림 자체를 줄이도록 시작 전에 모드 · 허용 도구를 정한다(§0 4번) |
| 워커 하트비트 주기 조절 | 해당 없음(워커가 하트비트를 보내지 않는다) | — |
| 터미널 해제 | 에이전트 보관이 세션을 닫는다. 워커가 따로 만든 터미널은 `paseo terminal ls` · `kill` | §5 |

## 0. 시작 전 점검 (환경마다 한 번)

1. `paseo --version` 과 `paseo status` — 데몬이 떠 있고 응답하는가. `paseo` 가 PATH 에 없으면 데스크톱 앱 번들 안의 CLI 를 쓸 수 있다(위치는 `paseo-help` 스킬 또는 Paseo 문서). 앱과 데몬 버전이 어긋나면 겉보기 버그가 많으니 맞춘다.
2. `paseo provider diagnostic claude` — 데몬이 쓰는 `claude` 실행 파일 · PATH · 버전이 정상인가. 데몬에서 Claude 가 로그인돼 있어야 한다.
3. 창구가 Paseo 에이전트인가 — 창구 세션의 환경에 `PASEO_AGENT_ID` 가 있는지(값은 교신에 쓴다) 확인한다. 창구가 Paseo 밖의 일반 터미널에서 도는 Claude Code 면 워커가 창구에 메시지를 보낼 수 없고 자동 알림도 오지 않는다(미측정 — 이 경우는 이 스킬의 범위 밖으로 둔다).
4. 무인 워커가 권한 요청에서 멈추지 않도록 사용자와 확인한다 — 모드(`paseo run --mode <모드>`, 목록은 `paseo agent mode <id> --list`)와 Claude 공급자 옵션(허용 도구 · 샌드박스 · 권한 규칙, 설정 파일 `agents.providers.<id>.options`). 허용 범위를 넓히는 설정은 사용자가 정한다.
5. agent team 은 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` 이 필요하다. 워커를 띄울 때 `paseo run --env CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` 로 주거나(옵션은 도움말에서 확인함), 공급자 설정의 `env` 에 둔다(`paseo reload` 로 반영). 이 값이 Paseo 가 띄운 Claude 세션에 실제로 전달돼 팀 기능이 켜지는지는 미측정이다.
6. 처음 쓰는 환경이나 버전이 바뀐 뒤에는 읽기 전용 시험 1회 — 워커 1명 ＋ 이름 있는 팀원 2명의 직접 왕복 ＋ 창구와의 교신(`status` · `ask` · 답 · `worker_done` 헤더 메시지). 「된다/안 된다」는 환경마다 다시 잰다. 이 시험은 파일을 바꾸지 않는다.
7. 버전이 맞는 사용법 = `paseo --help` · `paseo <명령> --help`, 공개 문서 색인 `https://paseo.sh/llms.txt`, 설치돼 있으면 `paseo` · `paseo-help` 스킬. 옛 메모 명령을 그대로 쓰지 않는다. 저장소의 gitignore 대상 파일(예: 환경 파일)은 새 worktree 에 자동으로 따라가지 않으므로 필요하면 `.worktreeinclude` 로 복사하게 한다(문서 확인함).

## 외부 가정 실측 (plan 전에)

- 설계가 외부 서비스의 동작(인증 공급자 · 결제 · 외부 API 가 무엇을 검증하고 무엇을 거절하는지)에 기대면, **plan 을 쓰기 전에 창구가 실제 요청으로 확인한다.**
- 확인한 사실은 워커 명세에 「실측」 으로 적고, 확인하지 못한 것은 「미확인 — 설계가 이것에 기댄다」 로 적는다.
- 검토 · 리뷰 · 보안 검수는 외부에 대한 틀린 가정을 잡지 못한다. 세 단계가 모두 같은 가정을 전제로 통과하고, 배포 뒤 실측에서야 틀린 것으로 드러나 끝낸 작업을 다시 열게 되는 일이 생긴다.
- 사용자에게 올리는 승인 요청에는 미확인 항목을 요약 맨 위에 둔다.

## 트랙 나누기 (워커를 띄우기 전에)

트랙은 워커 한 명이 맡는 작업 묶음이다. 잘못 나누면 워커끼리 같은 파일을 고쳐 충돌하거나, 서로의 결과를 기다리며 멈춘다.

**1. 무엇을 한 트랙으로 묶는가**

| 기준 | 판단 |
| --- | --- |
| 같은 파일을 고치는 일 | 한 트랙으로 묶는다. 기능이 달라도 파일이 겹치면 나누지 않는다 |
| 저장소가 다른 일 | 트랙을 나눈다. 저장소마다 브랜치와 작업 폴더가 따로다 |
| 같은 저장소, 겹치지 않는 파일 | 나눌 수 있다. 다만 공유 파일(설정, 공통 모듈, 계약 정의, 잠금 파일)을 함께 건드리는지 먼저 확인한다 |
| 브랜치 규칙이 「이슈 하나에 브랜치 하나」 인 프로젝트 | 트랙 하나가 브랜치 하나다. 같은 파일을 고치는 여러 이슈는 순서대로 한다 |

- 나누기 전에 각 일이 고칠 파일 목록을 대략 뽑아 겹침을 본다. 기능 이름만 보고 나누지 않는다.
- 겹침이 애매하면 묶는다. 묶어서 느려지는 비용보다 충돌을 푸는 비용이 크다.

**2. 트랙 사이의 약속**

한 트랙이 만드는 것을 다른 트랙이 쓰면(API 형태, 메시지 형식, 테이블 구조, 설정 이름) 약속 문서를 둔다.

- 약속 문서는 **만드는 쪽 워커 한 명이 쓴다.** 쓰는 쪽은 읽기만 한다.
- 쓰는 쪽의 이견과 질문은 창구를 거친다. 워커끼리 직접 고치게 두지 않는다. 약속이 바뀌면 창구가 양쪽에 알린다.
- 약속 문서는 두 워커의 작업 폴더 밖, 양쪽이 절대경로로 읽을 수 있는 곳에 둔다.
- 약속에는 값의 형식과 출처, 실패했을 때의 응답, 배포 순서를 적는다.

**3. 순서 의존**

- 약속을 만드는 트랙이 먼저 요구사항과 약속 초안을 낸다.
- 쓰는 트랙은 그동안 약속에 기대지 않는 부분(현행 분석, 자기 쪽 결정 항목)부터 진행하고, 만드는 쪽에 바라는 것을 적어 창구에 보낸다.
- 한 트랙의 결과가 나와야만 다른 트랙을 시작할 수 있으면 병렬이 아니다. 순서대로 하고, 앞 트랙이 끝난 뒤 뒤 트랙의 워커를 띄운다.

**4. 함께 나가야 하는 변경**

한쪽만 먼저 나가면 동작이 깨지는 변경은 머지와 배포를 묶는다.

- 「머지는 트랙마다」(§1 창구 절차)의 예외다. 창구는 **모든 트랙이 머지 준비가 된 뒤에** 머지를 시작한다.
- 순서를 정하고 그 이유를 약속 문서에 적는다. 기준은 「어긋난 동안 사용자가 겪는 실패가 더 작은 쪽을 먼저」 다.
- 이행기를 둘지(옛 방식과 새 방식을 함께 받을지)는 사용자에게 묻는 항목이다. 이행기는 검사를 피하는 길을 열 수 있다.
- 되돌릴 때도 함께 되돌려야 한다는 점을 기록에 남긴다.

**5. 동시에 몇 개를 띄우는가**

- 워커와 팀원, 창구가 띄운 에이전트는 **같은 사용 한도를 나눠 쓴다.** 워커 수 × 팀원 수가 한도를 정한다.
- 무거운 시험과 브라우저, 포트는 한 번에 한 트랙만 쓴다(§1 창구 절차). worktree 가 달라도 프로세스는 같은 기계의 네트워크 포트를 나눠 쓴다(Paseo 문서 확인함). 이런 자원이 필요한 단계가 겹치면 병렬의 이득이 줄어든다.
- 창구가 동시에 중계할 수 있는 수에도 한계가 있다. 승인 요청과 질문이 한꺼번에 몰리면 사용자가 판단하기 어렵다. 같은 성격의 승인은 묶어서 올린다.
- 처음에는 두 트랙으로 시작해 한도와 부하를 본 뒤 늘린다.

## 1. 창구 절차

1. 라운드 식별 = Paseo 에는 Run 개념이 없으므로 라운드 이름을 정해 모든 워커에 `--label round=<이름>` 을 붙인다. 창구는 라운드 기록 파일(작업 폴더 밖)에 워커 명부(트랙 · 워커 ID · 작업 공간 ID · 브랜치), 대기 질문 목록, 처리한 메시지 번호를 적는다. 창구 자신의 ID 는 `PASEO_AGENT_ID` 에서 읽는다.
2. 트랙은 「트랙 나누기」 절의 기준으로 나눈다. 트랙마다 `paseo workspace create --isolation worktree ...`(`--mode branch-off --new-branch <브랜치> --base <기준 ref>`)로 작업 공간을 만들고 `paseo workspace ls --json` 으로 Paseo 가 인식하는지 본다. 기준 ref 는 명시한다(`origin/<브랜치>` 는 원격 추적 브랜치, `refs/heads/<브랜치>` 는 로컬 — 문서 확인함). 작업 공간 ID(`workspaceId`)가 Paseo 에서 worktree 를 가리키는 키다.
3. 워커는 한 명씩 띄운다 = `paseo run --workspace <workspace-id> --provider claude --title "<라벨>" --label round=<이름> --label track=<트랙> --env CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 --no-wait --quiet "<첫 지시>"`(모드 · 모델은 「모델」 절과 §0 4번). `paseo run` 은 프롬프트를 인자로만 받으므로 명세가 길면 명세를 작업 폴더 밖 파일로 쓰고 첫 지시를 「이 파일을 끝까지 읽고 그대로 착수」 + 절대경로로 한다. 출력된 에이전트 ID 를 명부에 적고 `paseo ls --label round=<이름>` 으로 상태를 본다. 명령이 실패하면 재실행하기 전에 `paseo ls -a --label round=<이름>` 으로 이미 만들어졌는지 먼저 본다(중복 워커 방지).
4. 받은편지함 = 창구는 워커를 띄운 뒤 턴을 끝내고 기다린다. 워커의 `paseo send` 메시지는 창구의 턴이 끝나면 전달되고(기본 `queue`), MCP 경로를 켰다면 워커의 완료 · 오류 · 권한 요청 알림도 온다. 도착한 것은 헤더(§4)로 종류를 가르고 배치를 전부 처리한 뒤 다음 대기로 간다. 한 워커의 턴 종료만 필요하면 `paseo wait <id> --timeout <초>` 를 백그라운드로 건다. 빈 대기·시간 초과는 실패가 아니라 체크포인트다(`wait` 의 시간 초과 종료 코드는 미측정).
5. 무보고 정지 감시 = Paseo 알림은 턴 종료 · 오류 · 권한 요청만 알려 준다(CLI 경로에서도 오는지는 미측정). 알림 없이 긴 턴이 이어지는 경우는 창구가 하트비트로 점검한다 — `paseo heartbeat create --cron "*/30 * * * *" --max-runs <n> --expires-in <기간> "<점검 지시>"`. 점검 지시 = `paseo ls --label round=<이름>` 으로 상태 · `paseo permit ls` 로 대기 중 권한 요청 · 워커별 `paseo logs <id> --tail <n>` 으로 마지막 활동을 보고, 이상이 없으면 한 줄만 답하고 턴을 끝낸다. 하트비트는 창구 대화에 프롬프트를 넣으므로 주기를 길게 두고(예: 30분) 라운드가 끝나면 `paseo heartbeat delete <id>` 로 지운다. 하트비트 프롬프트가 사용자 입력과 어떻게 섞이는지는 미측정이다.
6. 워커 질문 답 · 지시 = `paseo send <워커 id> --no-wait --prompt-file <경로>`(짧으면 인자). 답은 첫 줄에 질문 번호를 되돌려 쓴다(§4). `--behavior` 는 메시지가 기다릴 수 없을 때만 쓴다 — 방향 수정은 `steer`, 즉시 중단은 `interrupt`. 응답의 안내(`guidance`)에서 메시지가 대기 중이라고 나오면 같은 메시지를 다시 보내지 말고, 기다릴 수 없는 것이면 짧은 후속을 `steer` 로 보낸다(Paseo 문서 지침).
7. 공유 자원은 창구만 배정한다(한 번에 한 트랙). 무거운 테스트 풀스위트 동시 실행이 기계 부하의 주범이다. 포트도 같은 기계를 나눠 쓰므로 슬롯에 포함한다.
8. 머지는 창구만, 트랙마다 한다(몰아서 금지) — 함께 나가야 하는 변경은 예외(「트랙 나누기」 4): 넘김 산출물 점검 → 기계 게이트(몇 개가 실제로 돌았는가부터) → 창구 직접 확인 → 머지 · 남은 트랙에 통지.
9. 워커 상태 = `paseo ls --label round=<이름>`(상태) · `paseo inspect <id>`(상세) · 출력 = `paseo logs <id> --tail <n>`. 「응답 없음」은 종료의 증거가 아니다.

## 3. 워커 안 agent team

1. 역할 전원을 `Agent` 도구에 `name` 과 `model: sonnet` 을 주어 spawn 한다. 각 프롬프트 = 첫 줄 역할 ＋ 라벨 · 자기 `name` 과 함께 일할 팀원들의 `name`(누구에게 무엇을 보내는지) · 산출물 파일과 커밋 규칙 · 즉시 착수.
2. 매핑표 `name ↔ 역할 ↔ 라벨 ↔ 모델` 을 파일에 적고 커밋한다. 한 `name` 이 두 역할 칸에 나오면 겸직이다.
3. spawn 직후 팀원마다 고유 토큰 1왕복으로 살아 있는지 확인한다. 같은 왕복에서 자기 모델명을 답하게 해 Sonnet 인지 본다. 아니면 그 팀원을 끄고 `model: sonnet` 으로 다시 spawn 한다.
4. 흐름 = analyzer → plan-architect ↔ plan reviewer 직접 핑퐁(승인까지) → dev(실패하는 테스트 먼저) → tester(화면이 있는 트랙만) → reviewer → security(「보안 검수」 절) → 워커 최종 판정. 오류가 나오면 해당 단계로 되돌아간다.
5. 팀원은 자기 단계가 끝나면 결론 1통(커밋 해시 포함)을 워커에게 보낸다. 결론의 정본은 커밋된 파일이다.

## 4. 교신 규칙

| 경로 | 수단 | 규칙 · 주의 |
| --- | --- | --- |
| 창구 → 워커 | `paseo send <워커 id> --no-wait` (MCP `send_agent_prompt`) | 창구가 보내는 기본 동작은 `queue` — 워커가 턴 안에 있으면 그 턴이 끝난 뒤 전달된다. `steer` 는 워커가 다음 단계에서 읽는다(공급자가 못 따르면 `interrupt` 로 바뀐다). 읽기 전에 턴이 멈추면 steer 한 메시지는 사라지므로 꼭 도착해야 하면 `queue` 나 `interrupt`. 문서 확인함 |
| 워커 → 창구 | `paseo send <창구 id> --no-wait ...` | ★워커는 `--no-wait` 를 꼭 붙인다 — 도움말상 `--no-wait` 가 없으면 상대가 턴을 마칠 때까지 돌아오지 않으므로 창구가 워커를 기다리고 워커가 창구를 기다리는 정체가 생길 수 있다(실제 동작은 미측정). 보낸 뒤에는 턴을 끝내고 답을 기다린다 |
| 워커가 창구 지시 읽기 | 별도 명령이 없다 | 창구의 지시 · 답은 워커의 다음 턴으로 도착한다. 워커가 턴 밖(idle)이면 그 메시지가 새 턴을 여는 것으로 보이나(문서: 받는 에이전트는 자기 기존 대화에서 프롬프트를 받는다) 모양은 미측정이다. 워커는 턴 밖에서는 아무것도 보낼 수 없으므로 보고 · 질문은 깨어 있는 턴 안에서 보낸다 |
| 워커 ↔ 팀원 | `SendMessage`(`name`) | Claude Code 기능. 아래는 Orca 환경에서 관측한 동작이며 Paseo 에서는 미측정이다 — 팀원 → 워커 메시지는 워커 턴 도중엔 보류되고 턴을 끝내면 새 턴으로 도착한다(유실 아님) |
| 팀원 ↔ 팀원 | `SendMessage`(상대 `name`) | Claude Code 기능. Orca 환경에서 관측(Paseo 미측정): 워커가 턴 안에 있어도 전달 · 워커 중계 없음 · 워커는 원문 대신 idle_notification 의 요약만 본다 |

**메시지 헤더 규칙** — Paseo 에는 메시지 종류 구분이 없으므로 모든 워커 → 창구 메시지는 첫 줄을 이렇게 쓴다: `[종류] 워커이름 번호`. 종류는 `status`(통지 · 슬롯 요청) · `ask`(결재 · 질문) · `merge_ready`(머지 요청) · `escalation`(막힘) · `worker_done`(종결, 1회). 번호는 워커별로 1부터 올린다(질문은 `Q-<n>`).

- 창구는 헤더로 종류를 거르고, 질문은 대기 질문 파일에 적은 뒤 답한다. 답의 첫 줄은 `[reply] Q-<n>` 으로 시작한다. 워커는 답이 없으면 같은 번호로 다시 보낸다.
- 같은 번호가 두 번 오면 한 번만 처리한다(중복 방지). 처리한 번호는 라운드 기록 파일에 적는다.
- 워커의 `worker_done` 은 「턴이 끝났다」 와 다르다. Paseo 알림은 중간에 턴이 끝나도 오므로, 창구는 알림이 아니라 `worker_done` 헤더 메시지와 커밋된 최종 기록 파일로 종결을 판정한다.

**그 밖의 규칙**

- 워커는 팀원 회신을 기다릴 때 턴을 끝낸다. 팀원이 한 턴을 마칠 때마다 idle_notification 이 워커를 깨운다 ⇒ 할 일이 없으면 도구 호출 없이 한 줄로 턴을 닫는다(토큰 절약).
- 종료한 팀원의 묵은 메시지가 뒤늦게(다음 라운드에) 섞여 올 수 있다(Orca 환경에서 관측, Paseo 미측정) ⇒ `teammate_id` · `summary` 로 거른다.
- ★메시지 본문에 백틱을 넣지 않는다 — 셸이 명령 치환으로 먹어 본문이 잘린 채 전송될 수 있다(셸의 일반 동작). 길거나 코드 조각이 필요한 본문은 파일로 만들어 `paseo send --prompt-file <경로>` 로 넘긴다(옵션은 도움말에서 확인함).
- 한 턴 안에서 결과가 꼭 필요한 짧은 조회는 이름 없는 서브에이전트가 맞다(결과가 턴 도중에도 도착한다 · `model: sonnet`). 역할 칸은 이름 있는 팀원이 채운다.
- ★in-process 팀원이 `run_in_background` 로 건 긴 작업의 완료 알림이 그 팀원을 깨우지 못한 사례가 Orca 환경에서 있었다. 긴 실행은 전경에서 기다리게 하거나, 워커가 끝날 시각에 `SendMessage` 로 깨운다. 창구는 결과 파일과 프로세스 수로 직접 확인할 수 있게 결과를 파일로 남기게 한다.
- 사용 한도: 창구가 `paseo usage ls --json`(`--refresh` 로 캐시 우회)으로 직접 잰다. 라운드 착수 전 여유를 확인하고, 여유가 적으면 「현재 단계 커밋 후 대기」 로 멈춘다(idle 팀원·워커는 토큰을 거의 쓰지 않는다). 출력에 Claude 의 5시간 · 주간 · 모델별 창이 나오는지는 미측정이다 — 나오지 않으면 `[미측정]` 으로 적고 워커 수를 보수적으로 둔다.

## 5. 종료 — 일이 끝난 팀원·워커는 바로 끈다

- 팀원 = `TaskStop`(또는 `shutdown_request`) → 팀 구성에서 빠졌는지 확인.
- 워커 = 창구가 완료 보고를 검증(헤더 메시지 ＋ 커밋된 최종 기록 파일) → 작업 폴더에 미커밋 · 미추적이 없고 브랜치가 필요한 곳에 올라갔는지 확인 → `paseo archive <id>`(실행 중인 에이전트에만 `--force` 가 필요하고 진행 중인 턴을 끊으므로, 턴이 끝난 것을 확인한 뒤 쓴다) → 해제 대상 0 = `paseo ls --label round=<이름>` 이 비었다(기본 목록은 보관된 에이전트를 뺀다 — 도움말 확인함). 워커가 따로 만든 터미널이 있으면 `paseo terminal ls` 로 보고 `paseo terminal kill <id>`.
- ★작업 공간을 보관하면 Paseo 가 관리하는 worktree 디렉터리가 지워진다(그 worktree 를 쓰는 마지막 작업 공간을 보관할 때 — 문서 확인함). 머지와 push 가 끝나고 「그 세션만 아는 값」 을 회수한 뒤에만 `paseo workspace archive <workspace-id>` 를 한다. 머지 전에 작업 공간을 보관하지 않는다.
- ★부모를 보관하면 자식이 함께 보관된다(SDK 문서 확인함). 라운드 중에 창구 세션을 보관하거나 새로 시작하지 않는다. 사용자가 워커를 독립시키려면 `paseo agent detach` 를 직접 한다(MCP 에는 없다 — 사용자 행동이다).
- 유지하는 경우는 하나 — 다음 작업을 같은 세션이 이어받는 게 나을 때(쌓인 맥락이 쓰일 때). 이때는 같은 워커에 `paseo send <워커 id>` 로 새 지시를 보낸다(같은 작업 공간 안에서만 가능하다. 다른 worktree 가 필요하면 새 워커).
- 라운드가 끝나면 워커와 팀원 전원을 종료하고 다음 라운드는 새 세션에서 시작한다(잔여 컨텍스트는 비용이 아니라 부채다). 창구가 만든 하트비트도 지운다.
- 끝내기 전에 「그 세션만 아는 값」을 파일로 회수한다 — 종료가 그것을 지운다.

## 6. 판정 술어 — 「통과」를 적기 전에

- ★**게이트는 돌리지 않은 것을 통과시킨다.** 빌드 캐시가 있으면 검사 스크립트가 전체 태스크 가운데 일부만 실제로 실행하고도 PASS 를 낼 수 있다(요약줄에 「캐시 N / 전체 M」 이 찍힌다). ⇒ 머지 직전 판정은 **머지될 트리에서 창구가 캐시 무시로 직접** 돌린다. 판정 = 종료 코드 ＋ **실제로 돈 태스크 수**.
- ★**강제 실행의 증거 문자열을 확인하고 센다.** 캐시 무시 실행임을 보여 주는 문자열은 도구마다 다르다. 엉뚱한 문자열(예: 캐시 미스 표시)로 세면 0건이 나오고 그 0을 「깨끗함」으로 읽게 된다. 도구가 바뀌면 그 도구의 문자열을 먼저 확인한다.
- ★**실패 계수는 요약줄의 수와 줄머리로 센다.** 기호(`×` 등)로 세면 테스트 **이름 안의 같은 기호**까지 세어 실제보다 부풀려진다.
- ★검사 스크립트의 주석·`TODO` 를 먼저 읽는다 — 스크립트가 자기 구멍을 이미 적어 두는 경우가 있고, 그걸 읽기 전에 결과를 인용하면 틀린 결론을 쓰게 된다.
- ★리뷰어에게 「테스트를 green 으로 유지하는 **틀린** 구현」을 실제로 만들어 보게 한다(§역할의 필수 문장). 이 점검은 구멍이 구현이 아니라 테스트에 있는 경우를 드러내고, 그러면 제품 코드는 그대로 두고 테스트를 보강해 닫는다.
- ★못 잰 것은 `[미측정]` 으로 남기고 통과로 세지 않는다. 판정문에 **무엇을 못 쟀는지**를 함께 적는다.
- ★규율은 배포하는 사람(창구)에게 가장 늦게 적용된다 — 창구가 자기 규칙을 어기는 일은 워커나 게이트가 잡아 주는 경우가 많다. 창구 절차에는 기계 대응물을 둔다(메시지 처리 기록과 다음 대기를 한 단계로 묶기 · 머지는 서명이 붙는 경로로 · 서버 종료는 포트가 아니라 프로세스 전수로 판정).

## 7. `[미측정]` (시험 운영에서 확인할 것)

이 스킬은 Paseo 에서 한 번도 돌려 보지 않았다. 앞의 항목일수록 먼저 확인한다. 확인되면 이 목록에서 지우고 본문에 반영한다.

1. **독립 세션 안의 팀원 생성** — Paseo 가 띄운 Claude 워커가 `Agent` 도구로 이름 있는 팀원을 만들고, 팀원끼리 `SendMessage` 가 오가는가. 이 스킬 전체의 전제다.
2. **agent team 환경변수 전달** — `--env` 또는 공급자 `env` 로 준 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` 이 워커 세션에 전달돼 팀 기능이 켜지는가.
3. **CLI 경로의 알림** — `paseo run` 으로 만든 워커의 완료 · 오류 · 권한 요청 알림이 부모(창구)에게 가는가. 문서에서 확인한 것은 MCP `create_agent` 의 `notifyOnFinish`(기본 true)다. 오지 않으면 `paseo wait` 와 창구 하트비트로 메운다.
4. **메시지의 모양과 도착 시점** — 워커의 `paseo send` 와 알림이 창구 대화에 어떤 모양으로 들어오는가, 창구가 idle 일 때 즉시 새 턴이 열리는가, 사용자가 입력하는 중에 끼어드는가, 하트비트 프롬프트는 어떤가.
5. **`--no-wait` 없는 `send` 의 동작** — 도움말 문구대로 상대의 턴 종료까지 돌아오지 않는가(교착 위험).
6. **`steer` 지원** — Claude 공급자가 steer 를 지원하는가(지원하지 않으면 interrupt 로 바뀐다고 문서에 있다).
7. **창구가 Paseo 밖일 때** — 일반 터미널의 Claude Code 를 창구로 쓸 수 있는가(`paseo import` 로 가져오는 방법 포함).
8. **모델** — `--provider claude`(모델 생략)가 어떤 모델로 도는가. Paseo 세션에서 `Agent` 도구의 `sonnet` 별칭이 최신 Sonnet 으로 풀리는가.
9. **사용 한도** — `paseo usage` 가 Claude 의 5시간 · 주간 · 모델별 주간 창을 보여 주는가.
10. **`paseo wait`** — 시간 초과 때 종료 코드, 여러 워커를 동시에 기다리는 방법.
11. **첫 지시의 길이 한도** — `paseo run` 인자의 길이 · 셸 인용 한계(명세 파일 방식으로 피하는 것이 기본이다).
12. 워커가 `worker_done` 없이 오래 idle 일 때 Paseo 가 알림을 어떻게 내는가(턴이 끝날 때마다 오는가).
13. 팀원이 0명인 idle 에서 묵은 메시지가 배달되는가.
14. 한 워커 안 팀원 6~7명의 메모리 · 부하, 그리고 동시에 띄울 수 있는 워커 수의 한도.
15. 워커가 사용자의 전역 `CLAUDE.md` · 스킬을 실제로 읽는가(문서는 구성 · 스킬 · MCP 서버가 유지된다고만 적고 있다).
