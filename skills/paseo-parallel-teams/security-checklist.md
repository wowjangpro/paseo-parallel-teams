# 전역 보안 검수 체크리스트

> 코드 변경 후 보안 검수 때 **먼저** 읽는 공통 기준이다. 언어 · 프레임워크 · 서비스와 무관하게 웹 · API · 배치 · 관리 화면 · 모바일 앱에 공통으로 쓴다.
>
> - 절차(역할 · 흐름 위치 · 판정 · 지적 처리 · 보고 형식)는 같은 폴더 `SKILL.md` 「보안 검수」 절이 정본이다. 이 파일에는 절차를 적지 않는다.
> - 근거 문서 절(§2)의 법령 · 인증기준 이름은 국내 서비스 기준이다. 다른 법역이나 다른 인증 체계를 쓰는 조직은 프로젝트 체크리스트에서 근거를 바꿔 쓴다. 정책 문장과 통과 기준은 그대로 쓸 수 있다.
> - 프로젝트에만 있는 것(스택별 함정 · 먼저 볼 곳 · 보고서 경로 · 금지 동작 · 증적 위치)은 `{프로젝트 루트}/docs/security-review/checklist.md` 에 둔다. 이 파일 다음에 읽고, 두 파일이 겹치거나 다르면 **프로젝트 쪽이 우선**한다.
> - 특정 서비스의 취약점 위치 · 재현 방법은 적지 않는다.

## 사용 방법

- 정책마다 「해당 없음 / PASS / FAIL」 을 근거와 함께 판정한다. 정책의 **대상**에 해당하는 변경이 없으면 「해당 없음」 과 이유 한 줄로 넘긴다.
- 정책 문장 ＋ 통과 기준 형식이다. 통과 기준은 확인 방법의 최소선이며, **정책에 없는 취약점을 찾아도 보고한다**(목록은 하한이지 상한이 아니다).
- 검수 범위는 변경된 줄이 아니라 변경으로 **새로 열리거나 동작이 바뀐 경로 전체**(진입점 → 처리 → 저장소 · 외부 호출)다.

## 1. 등급 기준

| 등급 | 기준 |
| --- | --- |
| 긴급 | 비로그인 또는 아무 일반 계정으로 다른 사용자 · 조직의 데이터 · 계정 · 자산 · 서버를 건드릴 수 있다 |
| 높음 | 조건이 붙거나 범위가 제한되지만 정보 유출 · 권한 상승 · 금전 손실로 이어진다. **법령 · 고시 위반이 되는 결함은 최소 높음** |
| 중간 · 낮음 | 그 밖의 방어 약화 |

정책마다 적은 등급은 FAIL 일 때의 기본값이다. 실제 도달 조건(로그인 필요 여부 · 망 제한 · 필요한 사전 정보)에 따라 위 기준으로 올리거나 내린다.

## 2. 근거 문서와 약칭

| 약칭 | 문서 | 성격 |
| --- | --- | --- |
| 고시 | 개인정보의 안전성 확보조치 기준(개인정보보호위원회 고시, 2025-10-31 개정 시행 · 접근권한 · 접근통제 · 접속기록은 1년 유예) | 개인정보처리자 전체에 **강제** |
| ISMS | 정보보호 및 개인정보보호 관리체계 인증기준(ISMS-P 공통 보호대책 2.x) | 인증 의무 대상이면 **강제** |
| 개발보안 | 소프트웨어 개발보안 가이드(행정안전부 · KISA, 2021) 구현단계 보안약점 49개 — Ⅰ 입력데이터 검증 및 표현 · Ⅱ 보안기능 · Ⅲ 시간 및 상태 · Ⅳ 에러처리 · Ⅴ 코드오류 · Ⅵ 캡슐화 · Ⅶ API 오용 | 민간은 권고. ISMS 2.8.1 「안전한 코딩 기준」 으로 흔히 쓰인다 |
| 망법 | 정보통신망 이용촉진 및 정보보호 등에 관한 법률 | **강제** |

- **모든 정책의 공통 근거**: ISMS 2.8.1(보안 요구사항 정의) · 2.8.2(보안 요구사항 검토 및 시험). 정책별 근거에는 다시 적지 않는다.
- ★**원문 대조 전**: 근거의 조문 · 항목은 2차 자료와 기억으로 적었다. 고시 원문(국가법령정보센터), ISMS-P 인증기준 안내서, 개발보안 가이드 PDF 로 대조한 뒤 이 줄을 지운다. 그 전까지 심사 증적에 조문 번호를 인용하지 않는다.

## 3. 공통 정책

### A. 입력 처리

#### P1. 외부 입력은 쿼리 · 명령 · 코드에 바인딩으로만 넣는다

- 통과 기준: 외부에서 온 값(요청 · 파일 · 메시지 큐 · 외부 API 응답)이 SQL · NoSQL 질의 · 저장 프로시저 호출 · OS 명령 · 코드 평가 · 템플릿 · LDAP · XPath 문자열에 결합되는 곳 0건. 바인딩할 수 없는 자리(식별자 · 정렬 · 개수 제한 · 목록 길이)는 허용 목록으로만 받는다. 바인딩이 실제로 되는지(따옴표 안 자리표시자 등 드라이버 동작)도 본다.
- 대상: 질의 · 명령 · 템플릿을 만들거나 고친 변경, 그 질의에 값을 넘기는 경로.
- 기본 등급: 긴급
- 근거: 개발보안 Ⅰ SQL 삽입 · 코드 삽입 · 운영체제 명령어 삽입 · XML 삽입 · LDAP 삽입

#### P2. 파일 경로 · 저장 위치 · 업로드는 서버가 통제한다

- 통과 기준: 외부 입력으로 서버 파일 경로 · 오브젝트 스토리지 키 · CDN 경로를 만들지 않는다(정규화 후 허용 위치 검사). 업로드는 확장자 · 형식 · 크기를 허용 목록으로 받고 실행 가능한 위치에 두지 않는다. 다른 사용자의 파일을 덮어쓰거나 지울 수 없다.
- 대상: 파일 읽기 · 쓰기 · 업로드 · 다운로드 · 삭제 경로.
- 기본 등급: 긴급
- 근거: 개발보안 Ⅰ 경로 조작 및 자원 삽입 · 위험한 형식 파일 업로드

#### P3. 서버가 대신 보내는 요청과 리다이렉트는 대상을 통제한다

- 통과 기준: 외부 입력 URL · 호스트로 서버가 요청을 보내지 않는다(허용 목록 없으면 FAIL, 내부망 · 메타데이터 주소 차단). 리다이렉트 · 딥링크 대상은 허용 목록이다.
- 대상: 외부 URL 호출 · 웹훅 · 이미지 가져오기 · 리다이렉트 · 딥링크 처리.
- 기본 등급: 높음(내부망 도달 시 긴급)
- 근거: 개발보안 Ⅰ 서버사이드 요청 위조 · 신뢰되지 않은 URL 주소로 자동접속 연결

#### P4. 신뢰할 수 없는 데이터를 안전하게 해석한다

- 통과 기준: XML 외부 개체 처리를 끈다. 외부 입력을 언어 고유 직렬화 형식으로 역직렬화하지 않는다(필요하면 타입 허용 목록). 정규식 · 압축 해제 · 이미지 처리 등에 크기 · 시간 한도가 있다.
- 대상: XML · 직렬화 데이터 · 압축 파일 · 사용자 정규식을 다루는 변경.
- 기본 등급: 높음
- 근거: 개발보안 Ⅰ 부적절한 XML 외부개체 참조 · Ⅴ 신뢰할 수 없는 데이터의 역직렬화

#### P5. 출력은 문맥에 맞게 이스케이프한다

- 통과 기준: 외부 입력을 HTML · 스크립트 · 속성 · URL 문맥에 이스케이프 없이 출력하지 않는다(템플릿 원문 출력 · HTML 직접 삽입 API 사용처 점검). 응답 헤더에 외부 입력을 그대로 넣지 않는다. 관리 화면에 고객 입력이 표시되면 특히 본다(관리자 세션 탈취).
- 대상: 화면 · 템플릿 · 응답 헤더 · 메일 · 알림 본문을 만드는 변경.
- 기본 등급: 높음
- 근거: 개발보안 Ⅰ 크로스사이트 스크립트 · HTTP 응답분할

### B. 인증 · 세션

#### P6. 진입점은 기본으로 인증을 요구한다

- 통과 기준: 새로 열리거나 바뀐 엔드포인트 · 페이지 · 스크립트 · 메시지 소비자가 인증을 거친다. 인증 예외(공개 표시 · 가드 제외 · 프레임워크 밖 단독 파일)를 새로 만들었다면 사유와 대체 통제(서명 · 한도 · 노출 데이터 없음)가 있다. 선택 인증 경로에서 비로그인일 때 보호 데이터가 나가지 않는다. 프레임워크가 공개 메서드 · 파일을 자동으로 URL 에 연결하면, 내부용 함수는 외부에서 호출할 수 없게 막혀 있다(비공개 처리 · 라우팅 제외).
- 대상: 라우트 · 핸들러 · 컨트롤러 공개 메서드 · 단독 진입 파일을 추가하거나 인증 설정을 바꾼 변경.
- 기본 등급: 긴급
- 근거: 개발보안 Ⅱ 적절한 인증 없는 중요 기능 허용 · ISMS 2.5.3 사용자 인증, 2.6.3 응용프로그램 접근

#### P7. 인증 수단은 서버가 검증하고, 실패를 제한하고, 오류 시 막는다

- 통과 기준: 외부 신원 토큰(소셜 로그인 · 앱 스토어 · SSO)은 서버가 서명 · 발급자 · 대상 · 만료를 검증한다. 2차 인증에 고정 코드 · 우회 파라미터 · 디버그 분기 · 빈 값끼리 비교가 없다. 「인증 완료」 처리를 인증 없이 직접 호출할 수 없다. 로그인 · 인증번호는 일정 횟수 실패 시 접근을 제한한다. 관리 화면에 외부에서 접속할 때는 안전한 인증수단(2차 인증 등)을 거친다. 인증 · 권한 확인 중 오류가 나면 허용이 아니라 거부한다.
- 대상: 로그인 · 가입 · 계정 찾기 · 비밀번호 재설정 · 2차 인증 · 토큰 발급 경로.
- 기본 등급: 긴급
- 근거: 개발보안 Ⅱ 반복된 인증시도 제한 기능 부재 · 부적절한 전자서명 확인 · Ⅳ 오류상황 대응 부재 · 고시 제5조(접근 권한의 관리), 제6조(접근통제) · ISMS 2.5.3 사용자 인증, 2.6.6 원격접근 통제

#### P8. 세션 · 토큰은 위조할 수 없고 수명이 있다

- 통과 기준: 신원 · 권한을 서명 · 암호화되지 않은 쿠키나 클라이언트가 계산할 수 있는 값으로 판단하지 않는다. 세션 · 토큰은 만료 · 폐기(로그아웃 · 비밀번호 변경 시)가 있고 URL 로 전달하지 않는다. 로그인 시 세션을 새로 발급한다. 쿠키에 보안 속성(HttpOnly · Secure · SameSite)을 둔다.
- 대상: 세션 · 쿠키 · 토큰을 만들거나 읽는 변경.
- 기본 등급: 긴급
- 근거: 개발보안 Ⅱ 쿠키를 통한 정보노출 · Ⅵ 잘못된 세션에 의한 데이터 정보노출 · ISMS 2.5.2 사용자 식별

#### P9. 교차 출처 요청을 통제한다

- 통과 기준: 쿠키 세션으로 상태를 바꾸는 요청에 CSRF 방어가 있다. CORS 는 허용 출처를 명시하고, 자격증명 허용과 와일드카드 · 요청 출처 반사를 함께 쓰지 않는다.
- 대상: 상태 변경 요청 처리, CORS · 쿠키 설정 변경.
- 기본 등급: 높음
- 근거: 개발보안 Ⅰ 크로스사이트 요청 위조

### C. 인가

#### P10. 대상 객체의 소유자를 서버가 확인한다

- 통과 기준: 조회 · 수정 · 삭제 대상의 소유자(사용자 · 조직 · 테넌트)를 외부 입력이 아니라 검증된 세션 · 토큰에서 꺼낸다. 외부 입력 식별자로 대상을 고를 때는 질의 · 프로시저 조건에 소유자가 들어 있다(소유자를 넘기지 않으면 하위 계층도 막을 수 없다). 목록 · 검색 · 내보내기도 같은 조건을 쓴다.
- 대상: 식별자를 받아 데이터를 읽거나 바꾸는 모든 경로.
- 기본 등급: 긴급
- 근거: 개발보안 Ⅱ 부적절한 인가 · Ⅰ 보안기능 결정에 사용되는 부적절한 입력값 · 고시 제6조(접근통제 — 권한 없는 자에게 공개 · 유출 방지) · ISMS 2.6.3 응용프로그램 접근

#### P11. 기능 권한을 서버가 확인한다

- 통과 기준: 관리 · 운영 기능과 역할별 기능은 서버에서 권한을 검사한다(화면에서 버튼만 숨기면 FAIL). 요청 본문으로 권한 · 역할 · 소유자 · 금액 등 보호 필드를 바꿀 수 없다(입력 필드 허용 목록). 새 기능이 권한 체계(메뉴 · 역할 매핑)에 등록돼 있다.
- 대상: 관리 기능 · 역할별 기능 · 데이터 수정 API 를 추가하거나 바꾼 변경.
- 기본 등급: 긴급
- 근거: 개발보안 Ⅱ 부적절한 인가 · 중요한 자원에 대한 잘못된 권한 설정 · Ⅰ 보안기능 결정에 사용되는 부적절한 입력값 · ISMS 2.6.3 응용프로그램 접근

#### P12. 서비스 간 호출과 신뢰 경계를 인증한다

- 통과 기준: 서버 · 장비 · 배치 · 내부 서비스용 엔드포인트가 호출자 인증(서명 · 공유 비밀 · 상호 TLS 등)을 한다. 망 분리 · IP 제한만으로 막는다고 판정하지 않는다. 앞단(게이트웨이 · 프록시)이 넣어 주는 신원 값 · 클라이언트 IP 헤더는 그 앞단을 거쳐서만 들어온다는 근거가 있을 때만 믿는다.
- 대상: 내부용 · 운영용 · 서버 간 엔드포인트, 게이트웨이 · 프록시 헤더를 읽는 변경.
- 기본 등급: 높음(외부에서 도달하면 긴급)
- 근거: 개발보안 Ⅱ 적절한 인증 없는 중요 기능 허용 · Ⅶ DNS lookup 에 의존한 보안결정 · ISMS 2.6.1 네트워크 접근, 2.6.2 정보시스템 접근

### D. 비즈니스 무결성

#### P13. 금액 · 자산 · 수량은 서버가 정하고 한 번만 반영한다

- 통과 기준: 결제 · 지급 · 차감 금액, 포인트 · 재화 · 이용권 수량, 이용 시간 · 횟수를 클라이언트 값으로 정하지 않는다. 결제 결과 · 영수증은 서버가 발급처에 검증한다. 재전송 · 동시 요청으로 두 번 반영되지 않는다(멱등 키 · 잠금 · 상태 전이 검사). 음수 · 0 · 상한 초과를 거른다. 단계가 있는 흐름은 앞 단계를 건너뛸 수 없다.
- 대상: 결제 · 과금 · 재화 · 보상 · 이용권 · 다단계 처리 흐름.
- 기본 등급: 긴급
- 근거: 개발보안 Ⅰ 보안기능 결정에 사용되는 부적절한 입력값 · Ⅲ 경쟁조건(검사 시점과 사용 시점) · ISMS 2.10.4 전자거래 및 핀테크 보안

#### P14. 비용 · 피해가 생기는 기능에는 한도가 있다

- 통과 기준: 문자 · 알림톡 · 메일 · 푸시 발송, 인증번호, 외부 유료 API 호출, 대량 조회 · 내보내기는 인증을 거치고 사용자 · 대상 · IP 단위 한도가 있다. 수신 대상은 서버가 정한다(외부 입력 번호로 임의 발송 불가). 인증번호는 유효 시간과 시도 한도가 있다. 광고성 정보 수신 동의 · 거부 변경은 본인만 할 수 있다.
- 대상: 발송 · 인증번호 · 외부 유료 호출 · 대량 조회 · 수신 동의 경로.
- 기본 등급: 높음
- 근거: 개발보안 Ⅱ 반복된 인증시도 제한 기능 부재 · 적절한 인증 없는 중요 기능 허용 · 망법 제50조(영리목적 광고성 정보 전송 제한)

### E. 데이터 보호

#### P15. 개인정보 · 민감정보는 필요한 만큼만 내보낸다

- 통과 기준: 응답 · 화면 · 파일에 업무에 필요 없는 개인정보 필드가 없다(저장 모델 통째 반환 금지). 마스킹은 서버에서 한다(화면 마스킹만 있으면 FAIL). 로그 · 오류 응답 · 알림 · 분석 이벤트에 개인정보 원문 · 인증정보가 남지 않는다. 다른 사용자의 식별자가 응답에 섞이지 않는다.
- 대상: 개인정보를 읽어 응답 · 화면 · 파일 · 로그 · 외부로 내보내는 경로.
- 기본 등급: 높음
- 근거: 개발보안 Ⅳ 오류 메시지 정보노출 · Ⅱ 암호화되지 않은 중요정보 · 고시 제6조(접근통제 — 유출 방지) · ISMS 2.9.4 로그 및 접속기록 관리

#### P16. 인증정보 · 중요정보는 안전하게 저장하고 만든다

- 통과 기준: 비밀번호는 복호화할 수 없는 일방향으로, 사용자별 솔트와 반복 연산이 있는 안전한 알고리즘으로 저장한다. 법이 암호화를 요구하는 정보(고유식별정보 · 계좌 · 카드 · 생체인식정보 등)는 검증된 알고리즘 · 충분한 키 길이로 암호화한다(취약 알고리즘 · 고정 IV · 직접 구현 금지). 토큰 · 인증번호 · 임시 비밀번호는 암호학적으로 안전한 난수로 만든다.
- 대상: 비밀번호 · 인증정보 · 중요정보를 저장 · 비교 · 생성하는 변경.
- 기본 등급: 높음
- 근거: 개발보안 Ⅱ 솔트 없이 일방향 해쉬 함수 사용 · 취약한 암호화 알고리즘 사용 · 충분하지 않은 키 길이 사용 · 적절하지 않은 난수 값 사용 · 고시 제7조(개인정보의 암호화) · ISMS 2.7.1 암호정책 적용, 2.5.4 비밀번호 관리

#### P17. 전송 구간은 암호화하고 인증서 검증을 끄지 않는다

- 통과 기준: 앱 · 웹 · 서버 간 · 외부 연동 통신에서 인증서 검증 우회(모든 인증서 신뢰 · 호스트 검증 끄기 · 웹뷰 오류 무시)가 빌드 종류와 상관없이 없다. 평문 통신 허용 예외를 새로 만들지 않는다. 인증정보 · 개인정보가 평문 구간으로 오가지 않는다.
- 대상: 네트워크 클라이언트 · 웹뷰 · 앱 보안 설정 · 외부 연동 변경.
- 기본 등급: 긴급
- 근거: 개발보안 Ⅱ 부적절한 인증서 유효성 검증 · 고시 제7조(개인정보의 암호화 — 송수신) · ISMS 2.7.1 암호정책 적용, 2.10.5 정보전송 보안

#### P18. 비밀값은 코드 · 산출물 · 로그에 넣지 않는다

- 통과 기준: 변경에 새 키 · 비밀번호 · 토큰 · 개인키 · 접속 문자열 0건(주석 · 테스트 · 설정 예시 포함). 앱 · 프론트 번들 · 컨테이너 이미지에도 비밀값이 들어가지 않는다. 비밀값은 비밀 저장소 · 실행 시 주입으로 읽고, 환경(개발 · 검증 · 운영)마다 다른 값을 쓴다. 로그 · 오류 응답에 찍히지 않는다.
- 대상: 모든 변경.
- 기본 등급: 높음(운영 비밀이면 긴급)
- 근거: 개발보안 Ⅱ 하드코드된 중요정보 · 주석문 안에 포함된 시스템 주요정보 · ISMS 2.7.2 암호키 관리, 2.8.5 소스 프로그램 관리

### F. 구성 · 운영

#### P19. 운영 노출면을 최소로 둔다

- 통과 기준: 테스트 · 디버그 · 임시 경로와 개발용 분기, API 문서 화면이 운영에 노출되지 않는다. 오류 응답에 스택 · 질의 · 내부 경로 · 버전이 나가지 않는다. 기본 계정 · 기본 비밀번호가 없다. 컨테이너 · 프로세스는 최소 권한(관리자 권한 실행 금지)으로 돈다. 디렉터리 목록 · 백업 파일이 공개 경로에 없다.
- 대상: 라우트 · 설정 · 오류 처리 · 배포 정의(컨테이너 · 서버 설정) 변경.
- 기본 등급: 높음
- 근거: 개발보안 Ⅵ 제거되지 않고 남은 디버그 코드 · Ⅳ 오류 메시지 정보노출 · ISMS 2.10.3 공개서버 보안, 2.8.6 운영환경 이관

#### P20. 새 구성요소는 출처와 알려진 취약점을 확인한다

- 통과 기준: 추가하거나 버전을 바꾼 라이브러리 · 이미지 · SDK 에 알려진 고위험 취약점이 없다(패키지 관리자의 감사 기능 등으로 확인). 공식 저장소에서 받고 잠금 파일이 함께 바뀐다. 실행 중 외부 코드를 내려받아 무결성 확인 없이 실행하지 않는다.
- 대상: 의존성 · 기반 이미지 · SDK 를 추가하거나 바꾼 변경.
- 기본 등급: 높음(원격 실행 취약점이면 긴급)
- 근거: 개발보안 Ⅶ 취약한 API 사용 · Ⅱ 무결성 검사 없는 코드 다운로드 · ISMS 2.10.8 패치관리

#### P21. 개인정보를 다루는 관리 기능은 권한 변경과 접속을 기록한다

- 통과 기준: 관리 · 운영 화면의 권한 부여 · 변경 · 말소가 기록된다. 개인정보 조회 · 수정 · 삭제 · 내보내기 때 누가 · 언제 · 어디서 · 무엇을 · 어떤 업무로 했는지 접속기록이 남는다. 대량 내보내기는 사유를 받는다. 새 기능이 이 기록에서 빠지지 않았다.
- 대상: 개인정보를 다루는 관리 · 운영 화면과 그 API 를 추가하거나 바꾼 변경.
- 기본 등급: 높음
- 근거: 고시 제5조(접근 권한의 관리), 제8조(접속기록의 보관 및 점검) · ISMS 2.5.1 사용자 계정 관리, 2.5.6 접근권한 검토, 2.9.4 로그 및 접속기록 관리, 2.9.5 로그 및 접속기록 점검
